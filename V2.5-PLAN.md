# @strapi-community/dockerize v2.5 - Complete Rewrite Plan

## Context

The current tool (v1.x) is a plain JavaScript CLI that generates Docker files for Strapi projects. It works, but it's showing its age: no TypeScript, no tests, limited detection (asks too many questions instead of reading existing config), only supports npm/yarn, outdated dependencies, and no plugin architecture for extensibility.

v2.5 is a ground-up rewrite targeting modern tooling (Bun + TypeScript), smarter defaults via project detection, a plugin system for databases and package managers, optimized Docker templates, and comprehensive test coverage. The goal: smaller, faster, smarter, same great DX with emojis and personality.

## Branch

All work happens on a `v2` branch from main.

## Core Architecture

### Config System (`src/config/schema.ts`)

Replace the current global mutable `_config` object with Zod-validated typed config:

- **`DetectedConfig`**: All fields optional. Populated by auto-detection. Represents what we found.
- **`ResolvedConfig`**: All fields required. Populated after user confirms/fills gaps. Represents the final truth.
- Zod schemas provide both runtime validation and TypeScript types from a single source.
- Config is passed explicitly through function calls, never mutated globally.

Key types:
- `DatabaseClient`: `"postgres" | "mysql" | "mariadb" | "sqlite"`
- `PackageManager`: `"npm" | "yarn" | "pnpm" | "bun"`
- `Environment`: `"development" | "production" | "both"`
- `ProjectType`: `"js" | "ts"`
- `StrapiVersion`: `"v4" | "v5"`

### Smart Detection (`src/detection/`)

The current tool asks 8+ questions. v2.5 detects first, confirms second.

**Detection pipeline** (all run in parallel):

1. **Strapi detector** - reads `package.json`
   - `@strapi/strapi` version -> v4 or v5
   - `tsconfig.json` existence -> ts or js
   - Dependencies scan: `pg`, `mysql2`, `better-sqlite3` -> database hint

2. **Database detector** - reads `.env` + config files
   - Parse `.env` for `DATABASE_CLIENT`, `DATABASE_HOST`, `DATABASE_PORT`, etc.
   - Read `config/database.ts` or `config/database.js` -> regex extract client
   - Read `config/env/*/database.*` for environment-specific configs

3. **Package manager detector** - checks lock files
   - `bun.lockb` -> bun
   - `pnpm-lock.yaml` -> pnpm
   - `yarn.lock` -> yarn
   - `package-lock.json` -> npm
   - Fallback: check which binaries exist in PATH

4. **Environment detector** - parses `.env`
   - `NODE_ENV` value
   - All `DATABASE_*` variables with their values

**Detection priority** (when signals conflict):
1. `.env` values (highest)
2. `config/database.*` parsed values
3. `package.json` dependency presence
4. Defaults (lowest)

**UX flow after detection:**
```
  Detected configuration:

    Strapi v5 (TypeScript)
    Package Manager: pnpm
    Database: PostgreSQL on localhost:5432
    Database Name: strapi
    Environment: development

  Is this correct? (Y/n)
```

If user says no -> fall through to individual prompts for each field.
If something couldn't be detected -> prompt only for that specific field.

### Plugin System (`src/plugins/`)

Static registry pattern. All plugins compiled in. Interfaces designed for future external plugin support.

**DatabasePlugin interface:**
- `id`, `displayName`, `defaultPort`, `driverPackage`, `strapiClient`
- `composeService(config)` -> docker-compose service definition with health check
- `envVars(config)` -> environment variables for .env
- `healthcheck()` -> container health check config
- `v4DriverPackage` / `v5DriverPackage` -> version-aware driver packages

**PackageManagerPlugin interface:**
- `id`, `displayName`, `lockFile`
- `installCommand`, `buildCommand`, `startCommand`, `devCommand`
- `addPackageCommand(pkg)`, `removePackageCommand(pkg)`
- `dockerCopyFiles()` -> files to COPY in Dockerfile
- `dockerInstallStep(production)` -> RUN command for install
- `dockerBuildStep()`, `dockerStartStep(dev)` -> build/start commands

**Built-in plugins:**
- Databases: postgres, mysql, mariadb, sqlite
- Package managers: npm, yarn, pnpm, bun

**SQLite plugin** (new): No compose database service. Strapi container only. Volume mount for `.tmp` data directory. Driver: `better-sqlite3`.

### Dependency Installation (`src/actions/install-deps.ts`)

Auto-installs the correct database driver, version-aware:

- **Strapi v5**: Uses different peer dependency requirements than v4
- Detects what's already installed (reads package.json deps)
- Only installs if the driver is missing
- Uses the detected package manager to install
- Handles driver conflicts (e.g., switching from pg to mysql2: remove old, install new)

### Template System (`src/templates/`)

Keep LiquidJS. Templates receive a fully-resolved context built from config + plugin data.

Template context includes:
- Node version (v5 -> 22, v4 -> 20)
- Package manager plugin methods (copy files, install step, build step, start step)
- Database plugin methods (compose service, health check, env vars)
- Project name, environment, compose toggle, adminer toggle

## Docker Template Improvements

### Dockerfile improvements over current
- Proper multi-stage: base -> deps -> build -> runtime
- Non-root user (`node`) from the start
- Health check with configurable start period (40s for Strapi cold start)
- Better layer caching (package files first, then source)
- All 4 package managers supported
- Platform-aware (no hardcoded `linux/amd64`)

### docker-compose improvements over current
- Health checks on database services
- `depends_on` with `condition: service_healthy` (fixes the #1 pain point: database race conditions)
- Adminer is optional (prompted, defaults to yes in dev)
- SQLite mode: no database service, just the Strapi container
- Named volumes with project-prefixed names
- No hardcoded platform (was breaking ARM macs)

### Production Dockerfile improvements
- Minimal final stage (vips-dev only, no build tools)
- Production-only dependencies
- Proper COPY --chown for non-root user
- Explicit NODE_ENV=production

## Build & Distribution

**Development:**
```bash
bun run src/index.ts   # Direct execution, no build step needed
```

**Production build:**
```bash
bun build src/index.ts --target=node --outfile dist/index.js
```

Produces Node.js-compatible output so npx/pnpm dlx/yarn dlx all work without Bun installed. The `bin` field in package.json points to `dist/index.js` with `#!/usr/bin/env node` shebang.

**Constraint:** Cannot use Bun-specific APIs (Bun.file, Bun.write) in source code. Use `fs/promises` for all file operations. Bun-specific features only used in test runner and build tooling.

**package.json bin entries:**
- `strapi-dockerize` (primary)
- Keep old name as alias for backwards compat

**CI/CD:**
- `ci.yml`: On PRs -> `bun install && bun run lint && bun test && bun run build`
- `publish.yml`: On main push -> same + `npx semantic-release`

**Coverage target:** 90%+ on `src/config/`, `src/detection/`, `src/plugins/`, `src/generators/`, `src/utils/`

## Parallel Work Streams

This rewrite is designed for multi-agent parallel development. Six independent streams with minimal dependencies.

### Stream 1: Foundation (Core + Config + Detection)
**Files:** `src/index.ts`, `src/cli/**`, `src/config/**`, `src/detection/**`, `src/utils/env-parser.ts`
**Depends on:** nothing (this is the foundation)
**Delivers:** CLI that runs, detects project settings, outputs detected config

### Stream 2: Plugin System + All Plugins
**Files:** `src/plugins/**` (types.ts, registry, 4 DB plugins, 4 PM plugins)
**Depends on:** shared type interfaces (written first as contract with Stream 1)
**Delivers:** Complete plugin registry with all 8 plugins (4 databases + 4 package managers)

### Stream 3: Templates + Generators
**Files:** `src/templates/**`, `src/generators/**`, `src/utils/fs.ts`, `src/utils/backup.ts`
**Depends on:** plugin interfaces from Stream 2 (can stub initially)
**Delivers:** Given a ResolvedConfig, generates all Docker/compose/env files

### Stream 4: DX (UI + Prompts)
**Files:** `src/ui/**`, `src/prompts/**`
**Depends on:** DetectedConfig type from Stream 1
**Delivers:** Banner, detection display, confirmation flow, fallback prompts, spinners, logger

### Stream 5: Tests + CI
**Files:** `tests/**`, `.github/workflows/**`
**Depends on:** Streams 1-4 (writes tests as modules land)
**Delivers:** Full test suite, CI pipeline, fixture projects

### Stream 6: Dependency Actions
**Files:** `src/actions/**`
**Depends on:** plugin interfaces, detection
**Delivers:** v4/v5-aware auto-installation of database drivers

### Integration Order
1. Streams 1 + 2 agree on shared types (`src/plugins/types.ts` + `src/config/schema.ts`) first
2. All streams work in parallel
3. Integration: wire everything in `src/index.ts` and `src/cli/commands/default.ts`
4. Stream 5 completes integration tests last

### Dependency Graph
```
Stream 1 (Foundation) ──┐
                        ├──> Stream 5 (Tests)
Stream 2 (Plugins)     ─┤
                        ├──> Integration in src/index.ts
Stream 3 (Templates)   ─┤
                        │
Stream 4 (DX)         ──┘
Stream 6 (Actions)    ──┘
```

## Verification

### How to test the rewrite end-to-end

1. **Unit tests:** `bun test` passes with 90%+ coverage
2. **Lint:** `bun run lint` passes clean
3. **Build:** `bun run build` produces `dist/index.js`
4. **Manual test against real Strapi v5 project:**
   - Create a fresh Strapi v5 project: `npx create-strapi@latest my-test`
   - Run the tool: `bun run src/index.ts` from the Strapi project directory
   - Verify detection output is correct
   - Confirm detected settings
   - Check generated files: Dockerfile, Dockerfile.prod, docker-compose.yml, .env, .dockerignore
   - Run `docker compose up` and verify Strapi starts
5. **Manual test with npx:** `npm pack && npx ./strapi-community-dockerize-*.tgz`
6. **Test each database:** postgres, mysql, mariadb, sqlite
7. **Test each package manager:** npm, yarn, pnpm, bun
8. **Test reset command:** verify cleanup works
9. **Test with no detection possible:** verify fallback to full prompts
